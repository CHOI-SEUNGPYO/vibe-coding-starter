# 작업을 끝까지 연결하기

먼저 이 요청의 완료 조건을 관찰 가능한 동작으로 정한다. 예를 들어 “로그인이 된다”보다 “잘못된 비밀번호는 오류를 표시하고, 올바른 계정은 원래 가려던 화면으로 이동한다”가 검증에 유용하다. 사용자가 이미 정한 범위와 기술 선택을 존중한다.

## 작업에 필요한 맥락만 확인

- 현재 변경 사항, 해당 영역의 `AGENTS.md`, 관련 구현·테스트·실행 명령을 확인한다. 다른 사람이 바꾼 코드를 되돌리지 않는다.
- `.vibe/project.json`이 있으면 프로젝트의 검증 명령을 읽는다. 비어 있으면 실제 프로젝트 도구에 맞는 명령을 정하고 추가한다. 템플릿 자체의 테스트 통과를 제품 동작의 증거로 쓰지 않는다.
- 외부 API·라이브러리 버전에 달린 판단은 설치된 버전과 공식 문서로 확인한다. 연결된 MCP는 해당 서비스가 필요할 때만 쓴다.
- 답을 기다릴 필요가 없는 선택은 기존 코드의 관례를 따른다. 제품 동작을 바꿀 핵심 정보가 없을 때만 구체적으로 묻고, 독립적으로 가능한 작업은 계속한다.

## 작동하는 작은 단위로 구현

가장 작은 사용자 흐름을 먼저 연결한 다음 필요한 오류·빈 상태·접근성을 채운다. 추측으로 공통 계층이나 새 의존성을 만들지 않는다. 회귀 가능성이 있는 동작은 실패 조건을 재현하는 검사로 확인한다.

다른 에이전트를 쓴다면 탐색·구현·검증의 경계를 먼저 정한다. 같은 파일을 동시에 수정하지 않는다. 작은 작업에 역할을 억지로 늘리지 않는다.

## 증거를 남기고 마무리

변경 범위에 맞는 검사를 실행한다. 명령, 종료 결과, 아직 확인하지 못한 조건을 구분한다. UI 작업은 주요 화면 크기와 핵심 상호작용을 실제 브라우저에서 확인한다. 브라우저 도구가 없으면 검증했다고 말하지 않는다.

실패를 고친 뒤 해당 검사를 다시 실행한다. 관련 검사가 통과하면 이유 없이 전체 검사를 반복하지 않는다. 마지막에는 무엇이 달라졌는지, 어떻게 확인했는지, 남은 제약이 무엇인지 짧게 전달한다. 공개·배포·메시지 전송은 현재 요청에서 허용한 범위 안에서만 실행한다.

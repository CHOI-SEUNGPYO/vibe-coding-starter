# 첫 작업 지시 양식 — 웹앱

[README의 시작 순서](../README.md)를 따라 `web` 환경을 적용하고, Codex에서 **저장소 루트 폴더**를 연 뒤 새 채팅에 아래 내용을 붙여 넣으세요. 이 파일 자체를 실행하는 것은 아닙니다.

1. `[입력: ...]` 부분을 내 프로젝트에 맞게 바꿉니다. 기술 선택을 모르겠으면 `추천해줘`, 필요 없는 항목은 `없음`으로 적거나 지웁니다.
2. 핵심 기능은 첫 버전에서 사용할 3개 정도로 좁히고, 완료 조건은 직접 확인할 수 있는 동작으로 적습니다. 예: `저장한 책이 새로고침 후에도 목록에 남는다`.
3. 게시 범위는 `로컬 구현·검증까지`, `지정한 GitHub 저장소에 반영`, `지정한 서비스에 배포` 중 필요한 범위를 적습니다. 게시하려면 대상 저장소·브랜치나 서비스를 함께 적습니다. 비밀키·토큰·실제 개인정보는 양식에 넣지 않습니다.
4. 아래 코드블록 안의 내용을 통째로 복사합니다. 완성된 예시는 [README](../README.md)에 있습니다.

서버 API는 [API 양식](first-api-task.md), CSV 분석·시각화는 [데이터 양식](first-data-task.md), 작은 CLI 도구는 [minimal 양식](first-minimal-task.md), 반복 처리는 [자동화 양식](first-automation-task.md)을 사용하세요. [환경 사용 가이드](../docs/environments.md)에서 목적에 맞는 프로필을 고를 수 있습니다.

디자인 링크를 모르겠으면 [디자인 레퍼런스 가이드](../docs/design-references.md)를 참고하세요. 랜딩 페이지는 Lapa Ninja·Landbook, 목록·검색 중심 웹앱은 SaaSFrame·Mobbin에서 접근 가능한 사례를 비교하도록 요청할 수 있습니다.

```text
$task-delivery로 아래 프로젝트의 첫 버전을 구현하고 검증해줘.

프로젝트 정보
- 이름: [입력: 프로젝트 이름]
- 목적: [입력: 누구의 어떤 문제를 해결하는지 한 문장]
- 주요 사용자: [입력: 예: 독서 기록을 남기는 개인 사용자]
- 사용할 환경: web
- 화면 언어와 주로 쓸 기기: [입력: 예: 한국어, 모바일과 PC]

첫 버전의 핵심 기능
1. [입력: 사용자가 할 수 있어야 하는 첫 번째 행동]
2. [입력: 두 번째 행동]
3. [입력: 세 번째 행동]
- 이번에 제외할 기능: [입력: 예: 로그인, 결제, 다른 사용자와 공유]
- 대표 사용 흐름: [입력: 예: 책 등록 → 검색 → 메모 수정 → 새로고침 → 다시 확인]

기술과 데이터
- 기술 스택: [입력: 예: React + TypeScript + Vite / 추천해줘]
- 저장할 데이터: [입력: 예: 책 제목, 저자, 읽는 상태, 메모]
- 저장 방식: [입력: 예: 이 브라우저에만 저장 / 계정별로 서버에 저장 / 추천해줘]
- 데이터 유지 범위: [입력: 예: 같은 브라우저·주소에서 유지 / 여러 기기에서 같은 계정으로 공유]
- 로그인·권한: [입력: 예: 개인용이므로 로그인 없음 / 일반 사용자와 관리자 구분]
- 외부 연동: [입력: 서비스명과 용도 / 없음]
- 기존 코드·자료: [입력: 확인할 프로젝트 내 경로와 보존할 내용 / 없음]

디자인
- 원하는 분위기: [입력: 예: 읽기 편한 차분한 화면, 충분한 여백]
- 참고 사이트·화면: [입력: 링크와 참고할 요소 / 가이드에서 추천해줘]
- 꼭 유지할 요소: [입력: 브랜드 색상, 로고, 현재 디자인 규칙 / 없음]

완료 조건
1. [입력: 예: 정상 입력을 저장하면 목록에서 볼 수 있다]
2. [입력: 예: 데이터를 저장한 뒤 새로고침해도 다시 조회할 수 있다]
3. [입력: 예: 검색 결과가 없으면 현재 조건과 초기화 방법이 표시된다]
- 모바일·키보드·오류 상황에서 확인할 동작: [입력: 구체적인 동작 / 앱에 맞게 정해줘]

작업과 게시 범위
- 이번에 허용하는 범위와 대상: [입력: 로컬 구현·검증까지 / GitHub 저장소 URL과 브랜치 / 배포 서비스와 대상]

진행 방법
- AGENTS.md, docs/environments.md, docs/skill-routing.md를 읽고 현재 설정과 관련 코드를 확인해줘. 필요한 도구가 실제로 연결되는지 확인하고, 실패한 연결을 성공으로 보고하지 마.
- 새 웹앱은 apps/web에 만들어줘. 루트 package.json과 lockfile은 MCP 실행 환경용이므로 보존하고, 앱의 의존성과 실행 명령은 앱 폴더에서 관리해줘. 기존 앱이 있다면 현재 구조와 기술 스택을 우선해줘. 실제 동작하는 Python·패키지 관리자 명령을 확인하고, 프레임워크뿐 아니라 테스트 도구까지 충족하는 런타임 버전을 engines와 README에 반영해줘. 앱 잠금 파일을 만들며 빌드 산출물·로컬 시험 자료는 Git에서 제외해줘.
- 추천을 요청한 선택은 목적과 기존 코드에 맞게 정하고 이유를 간단히 알려준 뒤 구현을 이어가줘. 제품 동작을 결정할 핵심 정보가 없으면 그 부분만 물어보고, 독립적으로 가능한 작업은 진행해줘.
- 화면 작업에는 ui-ux-pro-max와 docs/design-references.md를 참고하고, 접근 가능한 레퍼런스 2~3개에서 적용할 요소를 골라줘. 로그인·유료 제한으로 볼 수 없는 자료는 확인했다고 하지 말고 공개 사례로 대체해줘.
- 구현에는 프로젝트의 Ponytail, React를 쓸 때는 React 지침, 원인이 불명확한 오류에는 디버깅 지침, 검토에는 Ponytail Review를 사용해줘. 다른 전문 지침은 설치되어 있고 실제 작업에 해당할 때만 적용해줘.
- 라이브러리 사용법은 설치 버전과 Context7 또는 공식 문서를 대조해줘. 버전이 불명확한 결과를 같은 버전이라고 단정하지 말고, 외부 검색에는 비공개 코드나 데이터를 보내지 마.
- 작업 크기에 맞춰 진행하고, 보조 에이전트는 독립적으로 나눌 수 있는 작업에만 써줘. 파일 담당을 나누고 최종 결과를 통합해줘.
- .vibe/project.json에 이 앱의 목표·완료 조건과 실제 타입 검사·테스트·빌드 명령을 등록해줘. 필요한 검사 스크립트를 앱에 만들고 실행 위치도 맞춰줘. starter 검사만 통과한 것을 앱 검증으로 설명하지 마.
- GitHub Actions도 이 검사 목록을 실행하므로, 앱 검사에 필요한 Node 준비·앱 의존성 설치 등 CI의 실행 단계도 함께 맞춰줘. CI는 커밋된 프로필을 check로 확인하고, 다른 프로필을 다시 적용하지 않도록 해줘.
- 개발 서버 실행 명령을 준비해줘. 계속 켜 둘 개발 서버는 종료되는 검사 목록과 별도로 실행하고, 시작 메시지뿐 아니라 실제 주소의 응답과 브라우저 도구의 접속을 확인해줘. 실패하면 서버 종료·주소·포트·접근 권한을 구분하고, 확인하지 못한 동작을 완료로 보고하지 마.
- python scripts/vibe.py verify를 실행하고, Playwright로 대표 흐름과 모바일·키보드·빈 상태·잘못된 입력·저장 실패 중 앱에 해당하는 동작을 확인해줘. 저장 실패 때 기존 데이터와 입력이 보존되는지, 대화상자의 Escape·취소·닫기·저장 및 삭제 취소 뒤 원래 버튼으로 포커스가 돌아오는지도 확인해줘. 실행하지 못한 검사는 이유와 함께 남겨줘.
- 브라우저에 저장하는 앱이라면 브라우저 프로필·주소·포트가 달라질 때의 저장 범위와 권장 접속 주소를 설명해줘. Playwright의 격리된 시험 데이터와 사용자의 일반 브라우저 데이터를 구분해줘.
- 위에서 지정한 범위까지 마무리하고, 실행 방법·접속 주소·검사 결과·남은 제한을 알려줘. 게시가 포함되면 게시한 위치와 원격 결과도 확인해줘.
```

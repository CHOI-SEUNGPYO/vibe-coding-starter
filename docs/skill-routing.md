# 목적별 스킬 조합

프로필은 사용할 수 있는 스킬을 설치한다. 에이전트는 실제 작업과 기술 스택에 맞는 부분을 읽는다. `task-delivery`가 완료 조건과 구현·검증을 연결하고, 전문 스킬은 해당 단계의 판단을 보완한다. 전체 플러그인의 자동 hook이나 별도 메모리 시스템은 설치하지 않는다.

## 공통 순서

1. **요청과 실행 방법 확인:** 현재 코드·변경·검사 명령을 읽고 필요한 완료 조건을 정한다.
2. **구현:** 프로젝트의 `ponytail`로 기존 코드·표준 기능을 우선 사용한다. 기본 강도는 full이며 사용자가 요청한 기능은 유지한다.
3. **원인 조사:** 원인이 불명확한 실패에 `debugging-and-error-recovery`를 적용한다. 재현·범위 축소·원인 수정·회귀 확인으로 진행한다.
4. **검증과 검토:** 실제 검사와 브라우저 확인 후 reviewer가 `ponytail-review`로 변경과 관련 호출부를 검토한다. 작은 수정은 주 에이전트가 직접 처리할 수 있다.
5. **게시:** 요청된 범위에서 `release-check`를 적용하고 원격 결과까지 확인한다.

짧은 수정에는 별도 명세 문서를 만들 필요가 없다. 요구사항이나 모듈 간 계약이 복잡한 작업에는 계획을 남기고, 독립 작업에만 `parallel-work`를 사용한다.

## 웹과 디자인

`ui-ux-pro-max`로 디자인 시스템·타이포·색·레이아웃 후보를 검색하고 [디자인 레퍼런스](design-references.md)에서 실제 사례를 비교한다. React/Next.js 코드일 때 `vercel-react-best-practices`로 waterfall·bundle·렌더링 문제를 점검한다. Playwright로 실제 흐름·긴 한글·작은 화면·키보드·빈 상태를 확인한다.

```bash
python .agents/skills/ui-ux-pro-max/scripts/search.py "Korean B2B request dashboard accessible" --design-system -p "Request Desk"
```

이 명령은 로컬 데이터에서 후보를 찾는다. 화면의 목적과 사용자 흐름을 먼저 정하고 검색 결과 중 필요한 원칙만 적용한다. 기존 프로젝트에서는 현재 디자인 시스템을 우선한다. `--persist`를 쓰면 디자인 문서를 파일로 남기므로 원하는 저장 위치를 확인한다.

검색 데이터는 영어 중심이다. 사용자는 한국어로 요청해도 되고 에이전트가 영어 검색어로 바꿔 사용한다. 검색 결과가 없거나 업무용 화면에 판매 페이지 패턴이 섞이는 등 목적과 맞지 않는 결과가 나오면 `--domain ux`, `--domain color`처럼 좁혀 다시 비교한다. 검색이 실행됐다는 사실만으로 추천이 적합하다고 판단하지 않는다.

```text
팀 요청 관리 화면을 만들어줘. SaaSFrame과 Mobbin에서 목록·필터·빈 상태를
참고하고 ui-ux-pro-max로 디자인 후보를 비교해줘. 현재 프레임워크를 유지하고,
React라면 Vercel 성능 지침도 적용해. 실제 저장과 모바일 흐름까지 확인해줘.
```

## API와 서버

`api-and-interface-design`으로 입력·응답·오류 계약과 재시도·중복 요청 처리를 정한다. PostgreSQL을 쓰면 `supabase-postgres-best-practices`로 인덱스·연결·권한·잠금을 검토한다. Supabase 서비스 계정을 자동 생성하거나 연결하는 스킬은 아니다.

```text
주문 생성 API를 추가해줘. 기존 API 계약을 확인하고 멱등키·중복 요청과
응답이 오기 전에 연결이 끊긴 경우도 다뤄줘. PostgreSQL을 사용한다면
트랜잭션과 제약 조건을 관련 지침으로 검토하고 실제 통합 테스트를 실행해줘.
```

## 데이터 분석

Python 프로젝트에는 `python-patterns`로 예외·타입·자원 관리·구조를 점검한다. 분석 질문과 검증할 지표를 먼저 정하고, Postgres를 사용할 때만 DB 지침을 함께 적용한다. 차트는 [Observable Plot](https://observablehq.com/plot/)과 [Vega-Lite 예제](https://vega.github.io/vega-lite/examples/)에서 목적에 맞는 표현을 참고한다.

```text
CSV의 월별 불량률을 분석해줘. 입력 스키마와 누락·중복을 먼저 확인하고,
Python 패턴 지침에 맞춰 재실행 가능한 흐름으로 만들어줘.
기간별 비교에 적합한 차트를 고르고 집계값을 작은 샘플로 검산해줘.
```

## 업무 자동화

외부 API 연결에는 API 설계 스킬, Python 구현에는 Python 패턴, 브라우저 조작에는 Playwright를 사용한다. [n8n 사례](https://n8n.io/workflows/)는 입력·분기·결과 흐름을 참고하는 용도다. PR 의견을 처리할 때는 연결된 GitHub 앱을 우선하고, CLI를 사용할 경우 `gh-address-comments`의 설치·인증 조건을 확인한다.

```text
승인된 폴더의 파일을 분류하는 자동화를 만들어줘. 먼저 dry-run으로
이동할 목록을 보여주고, 같은 작업을 두 번 실행하거나 중간에 실패해도
중복 처리·데이터 손실이 없도록 구현해줘. 실제 샘플로 검증까지 해줘.
```

## 겹치는 지시를 처리하는 기준

현재 사용자의 범위·언어·기술 선택·승인과 프로젝트의 실행 정책을 우선한다. 전문 스킬의 정해진 영어 문구, 일률적인 승인 대기, 전체 묶음 설치 요구를 현재 작업에 맞게 해석한다. 이미 요청된 구현·검증은 계속하고, 추가 권한이 실제로 필요한 동작만 구분한다.

Ponytail의 ultra 강도와 모델의 Ultra 추론 수준은 서로 다른 설정이다. 이 저장소는 모델 ID를 고정하지 않는다. 프로젝트 안의 Ponytail은 공개 원본에서 가져온 스킬이며, 전역 Engineering Suite의 자동 주입·상태 hook 기능을 추가하지 않는다.

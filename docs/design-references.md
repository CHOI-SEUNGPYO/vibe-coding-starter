# 디자인 레퍼런스를 찾고 구현에 연결하기

화면을 만들기 전에 **비슷한 사용 목적의 사례 2~3개**를 고른다. 랜딩 페이지는 내용의 순서와 시각적 인상을, 제품 화면은 사용자가 일을 마치는 흐름을 중심으로 본다. 아래 목록은 **2026-11-15**에 공식 페이지를 확인했다. 로그인·유료 제공 범위는 바뀔 수 있으므로 실제 사용할 때 해당 서비스에서 확인한다.

## 랜딩 페이지·브랜드·포트폴리오

| 사이트 | 특히 볼 것 | 접근 범위 |
| --- | --- | --- |
| [Lapa Ninja](https://www.lapa.ninja/) | 업종별 랜딩 페이지, hero·기능·가격·CTA 등 섹션 구성. 한 페이지의 설명 순서를 정할 때 출발점으로 쓰기 좋다. | 공개 갤러리 확인 |
| [Landbook](https://land-book.com/design/website/single-page) | 페이지 전체의 타이포그래피, 여백, 색 조합. 유사 업종과 스타일을 비교해 방향을 좁힌다. | 무료 범위와 Pro 기능이 나뉨. [공식 안내](https://land-book.com/pro) |
| [Recent](https://recent.design/) | 웹·인터페이스·브랜딩·모션을 함께 보며 표현 방식을 찾는다. | 공개 갤러리 확인. `godly.website`는 확인 시 이 사이트로 이동했음 |

처음부터 갤러리를 전부 훑기보다 “개발 도구 랜딩”, “작품 중심 포트폴리오”, “식당 예약”처럼 작업 목적을 먼저 정한다. 랜딩 페이지의 한 장짜리 이미지만으로 모바일 메뉴나 실제 성능까지 판단하지 않는다.

## 제품 UX·대시보드·SaaS

| 사이트 | 특히 볼 것 | 접근 범위 |
| --- | --- | --- |
| [Mobbin](https://mobbin.com/) | 실제 서비스의 모바일·웹 화면. 가입, 탐색, 설정 등 같은 작업의 화면을 비교한다. | 무료 가입과 유료 전체 접근을 구분. [공식 플랜](https://mobbin.com/pricing) |
| [SaaSFrame](https://www.saasframe.io/) | 대시보드, 계정 설정, 온보딩, 빈 상태, 추가·수정 화면. 업무용 제품의 정보 밀도와 상태 표현을 참고한다. | 공개 미리보기와 유료 전체 접근을 구분. [공식 플랜](https://www.saasframe.io/pricing) |

실제 제품을 만들 때는 완성 상태뿐 아니라 최초 진입, 로딩, 검색 결과 없음, 입력 오류, 저장 완료도 함께 설계한다. 대시보드는 카드 수보다 “지금 어떤 판단이나 행동을 도와야 하는가”를 먼저 정한다.

## 구현할 컴포넌트·인터랙션

| 사이트 | 잘 맞는 작업 | 사용할 때 확인 |
| --- | --- | --- |
| [shadcn/ui](https://ui.shadcn.com/) | React 제품 화면의 폼, 표, 대화상자, 내비게이션을 프로젝트에 맞게 구성 | 기존 UI 구조·스타일 도구와 호환되는 컴포넌트만 선택. 공개 문서·코드 제공 |
| [Radix UI](https://www.radix-ui.com/) | 키보드·포커스 동작이 중요한 메뉴, 팝오버, 대화상자 | Primitives와 Themes 중 필요한 층을 선택. 공개 오픈소스 라이브러리 |
| [Aceternity UI](https://ui.aceternity.com/) | 랜딩 페이지의 시각 효과, 섹션, 상호작용 | 공개 데모와 유료 All-Access 콘텐츠를 구분. [공식 이용 범위](https://ui.aceternity.com/pricing) |
| [Magic UI](https://magicui.design/) | React·Tailwind 기반의 강조 효과와 애니메이션 | 공개 오픈소스 컴포넌트와 별도 Pro 블록·템플릿을 구분 |

이 링크들은 프로젝트에 자동 설치되는 라이브러리가 아니다. 선택한 컴포넌트의 의존성·라이선스·키보드 동작·모션 감소 설정을 확인한 뒤 도입한다. 화면 하나를 위해 UI 라이브러리를 여러 개 추가하기 전에 기존 구성으로 구현 가능한지 살핀다.

## 사용성과 플랫폼 관례

| 공식 가이드 | 참고할 내용 |
| --- | --- |
| [Material Design 3](https://m3.material.io/) | 색·타이포그래피·상태·레이아웃의 공통 규칙. [Foundations](https://m3.material.io/foundations/)에서 접근성·디자인 토큰·상호작용 상태 확인 |
| [Apple Human Interface Guidelines](https://developer.apple.com/design/human-interface-guidelines) | Apple 플랫폼의 내비게이션, 입력 방식, 컴포넌트 사용 관례. 대상 플랫폼에 맞는 장을 선택 |

컴포넌트를 가져온 뒤에도 실제 제품에서 탭 이동, 포커스 표시, 화면 확대, 작은 화면, 긴 한글 문구를 확인한다. 시각적 완성도와 접근성 검증은 별도로 기록한다.

## 바이브코딩에 적용하는 순서

1. **화면의 일을 정한다.** 사용자, 첫 방문 이유, 가장 중요한 행동 하나, 반드시 표시할 정보를 적는다.
2. **사례 2~3개를 고른다.** 구조를 참고할 페이지, 시각적 방향을 참고할 페이지, 필요한 경우 사용자 흐름 사례를 선택한다.
3. **관찰을 구체적인 기준으로 바꾼다.** “깔끔하게” 대신 콘텐츠 최대 너비, 제목과 본문 크기 관계, 섹션 간격, 강조색 용도, 메뉴 위치, 입력 오류 표시를 적는다. 숫자는 실제 관찰과 프로젝트 필요를 근거로 결정한다.
4. **작은 화면까지 설계한다.** 넓은 화면의 여러 열이 어떻게 접히는지, 메뉴와 표가 어떻게 바뀌는지 정한다. 필요한 빈 상태·오류 상태도 함께 적는다.
5. **한 흐름을 구현하고 비교한다.** 브라우저에서 실제 화면을 열어 완료 조건을 검사한다. 배치, 타이포그래피, 간격, 상태, 동작 순서로 차이를 수정한다.

프로젝트 문서에는 아래처럼 짧게 남기면 다음 에이전트도 같은 방향을 이어갈 수 있다.

```text
화면 목적: 팀원이 오늘 처리할 요청을 찾고 담당자를 배정한다.
핵심 행동: 필터로 요청 찾기 → 상세 확인 → 담당자 배정.
참고 URL: 실제로 열어 확인한 페이지 2~3개.
구조: 왼쪽 탐색, 상단 검색·필터, 중앙 요청 목록, 상세 패널.
시각 기준: 중립색 바탕, 상태색은 의미가 있을 때만, 본문 가독성 우선.
상태: 최초 진입·로딩·검색 결과 없음·권한 부족·저장 실패·저장 완료.
검증: 작은 화면과 넓은 화면, 키보드 이동, 긴 한글 제목, 실제 저장 결과.
```

에이전트는 공개 페이지를 읽고 필요한 화면을 관찰하는 범위에서 레퍼런스를 사용한다. 로그인이나 구독이 필요한 자료는 사용자가 접근 가능한 범위에서만 확인한다. 페이지의 레이아웃과 인터랙션 원리를 참고하고, 다른 서비스의 로고·이미지·문구·유료 템플릿을 그대로 가져와 저장소에 재배포하지 않는다. 직접 구입하거나 라이선스가 확인된 자산은 그 조건에 맞게 사용한다.

추가 후보로 [Awwwards](https://www.awwwards.com/)와 [Page Flows](https://pageflows.com/)도 있다. 이번 자동 조회에서는 각각 응답 지연과 접근 제한으로 현재 본문을 확인하지 못했으므로, 무료 범위·기능에 대한 판단은 넣지 않았다.
